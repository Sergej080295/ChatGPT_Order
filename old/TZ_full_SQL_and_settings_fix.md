
# ТЗ: Переход на полноценный SQL‑бэкенд + фиксы сохранения настроек

## 0. Цели и контекст
- Устранить баг с «откатами» настроек (журнал, сопоставления и пр.): частичные сохранения не должны перезатирать ранее выставленные параметры.
- Подготовить систему к большому объёму данных (тысячи заказов / десятки тысяч стадий) — стабильность, скорость, отчётность.
- Сохранить совместимость с текущим фронтендом (`CRM.html` / `Planner_Codex_v3.html`), который ожидает единый JSON `/api/state`, и постепенно перевести его на гранулярные эндпоинты.

## Этап 1. Быстрый фикс настроек (без смены архитектуры) — сделать сразу

### 1.1. Сервер: **merge** настроек вместо полной перезаписи
В обработчике `PUT /api/state` добавить ветку `if (meta.stage === 'settings')`, которая:
1) читает текущее состояние из БД,  
2) точечно сливает («merge») **только** изменённые ключи настроек (`logLimit`, `crmStageMapping`, `extraTime.*`, `tableColumns.*` и т. п.),  
3) сохраняет результат.

Поддержать два режима:
- **merge** (по умолчанию): изменённые ключи переносятся, остальные сохраняются;
- **replace** (если `meta.settings.replace = true`): отсутствующие ключи считаются удалёнными (режим «забыть прошлые значения»).

**Критерии приёмки**
- Последовательные сохранения разных разделов настроек не приводят к откатам предыдущих значений.
- В режиме `replace` прежние соответствия (не переданные в теле) исчезают.

### 1.2. Клиент Planner: «не тянуть» старые сопоставления
- При сохранении сопоставлений (CRM → стадии) отправлять **только** актуально заполненные ключи, без подстановки предыдущих значений с клиента.
- Добавить чекбокс «Сбросить прошлые сопоставления» → при активном чекбоксе отправлять `meta.settings.replace = true`.

**Критерии приёмки**
- Если пользователь изменил часть соответствий и **не** включил «Сбросить…», старые незатронутые ключи сохраняются.
- Если включил — все неуказанные ключи удаляются, откатов нет.

### 1.3. UI настроек: фикс ширины и устойчивый список
Зафиксировать ширину диалога и ограничить высоту списка сопоставлений.
```css
/* Settings dialog sizing */
#settingsDlg{
  width: min(90vw, 960px);
  max-width: 960px;
}
.settings-mapping-list{
  max-height: 50vh;
  overflow: auto;
}
.settings-mapping-row{
  display: grid;
  grid-template-columns: 1fr minmax(0, 360px);
  column-gap: 12px;
}
```

**Критерии приёмки**
- Ширина диалога не «прыгает» при заполнении/очистке формы.
- Скролл внутри списка работает, остальной UI не смещается.

## Этап 2. Введение полной SQL‑модели с «мостом» к текущему фронту

### 2.1. Схема БД (PostgreSQL)
Создать следующие таблицы (DDL на усмотрение команды; ориентиры по полям ниже).

1) **stage_type** — справочник переделов  
`id, code (uniq), name, sort_order, is_active`

2) **customer_order** — заказы (ядро CRM)  
`id, order_no (uniq*), title, client, priority, due_date, created_at, updated_at, is_deleted`  
\* уникальность со скоупом по `is_deleted = false`.

3) **order_stage** — стадии (переделы) заказа (каркас для Ганта)  
`id, order_id → customer_order, stage_type_id → stage_type, hours, extra_hours, start_at, end_at, start_missing, end_missing, state, status, progress, use_reserve, orig_start_at, version, created_at, updated_at, is_deleted`  
Индексы: `(stage_type_id, start_at)`, `(order_id)`.

4) **stage_completion** — история «готово»  
`id, order_stage_id → order_stage, completed_at, source, note`

5) **stage_exception** — исключения/блокировки  
`id, order_stage_id → order_stage, kind, details(jsonb), created_at, resolved_at`

6) **capacity_by_stage** — производственные мощности  
`stage_type_id (pk) → stage_type, capacity_per_day`

7) **parallel_limits** — ограничения параллельности  
`code (pk), max_parallel`  (например: `proc`, `shear`, `pack`, `ship`)

8) **planner_settings** — настройки планировщика  
`id (pk=1), autosave_on, auto_optimize_on, shift_on_progress, storage_mode, extra(jsonb)`

9) **planner_activity_log** — журнал изменений  
`id, timestamp, stage, version, user_name, session, source, summary, diff(jsonb), orders_summary(jsonb), ip`  
Индексы по `timestamp`, `stage`.

**Критерии приёмки**
- Все таблицы созданы, FK/индексы на месте.
- Миграции повторно применимы (idempotent), rollback‑скрипт существует.

### 2.2. Миграция данных из текущего снимка
Единоразовый конвертер: прочитать текущий большой JSON (или `planner-state.json`) и разложить:
- `customer_order` — уникальные `order_no`;
- `order_stage` — каждая запись из t/переделов;
- `capacity_by_stage`, `parallel_limits` — из текущих конфигов;
- `stage_completion` — из `done`;
- `stage_exception` — из исключений;
- `planner_settings` — из `meta.settings` (если есть).

**Критерии приёмки**
- После миграции результат выборок из SQL покрывает данные текущего фронта.
- Контрольная сверка: количество заказов/стадий/готовностей совпадает.

### 2.3. Двойная запись (dual‑write) и обратная совместимость
- `PUT /api/state` (legacy): парсить снимок, транзакционно **апсертить** изменённые сущности в SQL **и** сохранять монолитный JSON как кэш/бэкап.
- `GET /api/state`: собирать JSON **из SQL** (вью‑модель) и возвращать его. Добавить `ETag/If-None-Match`.
- SSE `/api/events`: отправлять **дельты** (id заказа/стадии + изменённые поля), а не полный снимок.

**Критерии приёмки**
- Текущий фронт работает без изменений.
- Размер ответа `/api/state` стабильно ≤ прежнего; при неизменности — `304 Not Modified`.

## Этап 3. Гранулярные API и пагинация (подготовка фронта к большим объёмам)

### 3.1. Эндпоинты заказов
```
GET    /api/orders?query=&status=&limit=&cursor=   # список с пагинацией
POST   /api/orders                                  # создать
PUT    /api/orders/:id                              # обновить
DELETE /api/orders/:id                              # мягкое удаление (is_deleted=true)
```

### 3.2. Эндпоинты стадий (переделов)
```
GET   /api/stages?stage=laser&from=&to=&orderId=&limit=&cursor=
POST  /api/orders/:id/stages
PUT   /api/stages/:id
PATCH /api/stages/:id/status
POST  /api/stages/:id/complete     # создаёт запись в stage_completion
```

### 3.3. Настройки и мощности
```
GET   /api/settings
PATCH /api/settings                # merge/replace семантика
GET   /api/capacity
PUT   /api/capacity
GET   /api/parallel-limits
PUT   /api/parallel-limits
```

**Критерии приёмки**
- Все эндпоинты документированы (OpenAPI/Swagger).
- Поддержаны `limit/cursor` и стабильная сортировка результатов.

## Этап 4. Оптимизация производительности и устойчивости

### 4.1. Индексы и планы
Добавить/проверить:
- `order_stage(stage_type_id, start_at)` — Гант/календарь,
- частичный индекс по «текущим» (без `is_deleted`, `status in ('Выполняется','Ожидает')`).  
Материализованные представления для тяжёлых отчётов — по необходимости.

### 4.2. Конкурентность
- Оптимистические блокировки: `order_stage.version` инкремент; `WHERE version = :old`.
- При конфликте — HTTP 409 с payload: кто/когда изменил.
- Транзакции на пакетные операции.

### 4.3. Кэширование и сеть
- `ETag` на всех «тяжёлых» GET‑ответах.
- Сжатие ответов (gzip/br).
- SSE/WebSocket — только дельты.

**Критерии приёмки (нагрузочный тест)**
- Датасет: 10k заказов / 100k стадий.
- `GET /api/stages?stage=laser&from=&to=` — P95 ≤ 150 мс.
- `PATCH /api/stages/:id/status` — P95 ≤ 80 мс.
- `/api/state` при неизменности — 304 за ≤ 10 мс, при изменении — P95 ≤ 250 мс.

## Нефункциональные требования

### Безопасность и доступ
- Подключение к БД — через `DATABASE_URL`, поддержка SSL.
- Роли БД: `app_rw`, `app_ro`, отдельная `migration`.
- Маскирование чувствительных данных в логах.

### DevOps
- Миграции (`node-pg-migrate`/`knex`/`sql-migrate`) + rollback.
- Бэкапы БД: ежедневные, хранение ≥ 14 дней.
- Мониторинг: `pgbouncer`/`pg_stat_statements`, метрики API (latency, error rate).

### Логи и аудит
- `planner_activity_log` заполняется на все изменения (кто/что/когда, краткое summary, diff).

## Тест‑план (ключевые проверки)

1) **Фикс настроек**
- Сохранить `logLimit`, затем отдельно `crmStageMapping` → первое не сбрасывается.
- Сохранить новое сопоставление с `replace=true` → неуказанные ключи исчезают.

2) **Миграция**
- После мигратора число заказов/стадий/готовностей совпадает со старой системой.
- Случайные 10 заказов сверены вручную.

3) **Производительность**
- Нагрузочные тесты по критериям из Этапа 4.3.

4) **Конкурентность**
- Два параллельных апдейта одной стадии → один успешен, второй получает 409 с данными о конфликте.

5) **Совместимость**
- Текущий фронт без изменений работает через `GET/PUT /api/state` (мост к SQL).

## Что именно решит текущий баг с настройками
- **Server‑merge** настроек (Этап 1.1) исключит перезатирание ранее сохранённых ключей при поочерёдных апдейтах.
- **Client‑replace‑режим** (Этап 1.2) позволит «забывать» предыдущие соответствия, когда это требуется.
- **Фикс размеров окна** (Этап 1.3) уберёт «скачки» ширины диалога.
