# Поток данных заказов по переделам

Этот документ описывает, как заказы попадают в списки переделов в Планировщике PlanCore и какие артефакты участвуют в цепочке сохранения.

## 1. Сбор данных на клиенте
- При загрузке состояния `restoreState` запоминает снимок `modeScoped.crm.stageTasks`, в котором для каждого кода передела (`laser`, `bend`, `weld` и т.д.) хранится список карточек.
- Когда пользователь вносит изменения (перетаскивает карточки, правит готовность, меняет даты), `captureModeScopedState` формирует обновлённый снимок. Карточки сериализуются функцией `serializeTaskForModeSnapshot`, где фиксируются UID, стадия, маршрут и CRM-метаданные.
- При сохранении состояние отправляется на сервер через `/api/state` и в JSON попадают:
  - `t`, `done`, `trash`, `exc`, `res` — массивы активных задач.
  - `modeScoped.crm.stageTasks` и `modeScoped.crm.orders` — группировка задач по переделам и сохранённый порядок карточек.
  - `crm.boards` — список CRM-досок с заказами и их стадиями.

## 2. Нормализация на сервере
- Сервер парсит JSON и вызывает `extractStorageParts(snapshot)`:
  - Заказы CRM досок попадают в массив `orders` и одновременно строится отображение идентификаторов заказов.
  - Активные задачи и карточки переделов попадают в массив `tasks`. Для CRM-переделов им присваивается `bucket = 'crm_stage'`, а поле `stage` содержит код передела.
  - `modeScoped.crm.orders` превращается в `stageSequences` — порядок UID карточек в каждой колонке.
- Функция `ensureModeScopedConsistency` восстанавливает `modeScoped.crm.stageTasks`, используя задачи из `tasks` и порядок из `stageSequences`. С версии, добавленной в этом коммите, учитываются как `bucket === 't'`, так и `bucket === 'crm_stage'`, поэтому карточки CRM не теряются при повторной сборке состояния.

## 3. Хранение в SQL
- При сохранении выполняется `persistSnapshotWithSql`:
  - Таблицы `pc_orders`, `pc_order_tasks` и `pc_stage_sequences` очищаются и заполняются актуальными данными.
  - Карточки переделов записываются в `pc_order_tasks` с `bucket = 'crm_stage'` и полями прогресса, дат, исполнителя.
  - Итоговый снимок сохраняется в `pc_settings` под ключами `snapshot_base` и `snapshot_full`.

## 4. Сбор состояния при загрузке
- `loadSnapshotFromDatabase` читает таблицы SQL и собирает единый снимок через `assembleSnapshot()`:
  - Для каждой строки из `pc_order_tasks` восстанавливаются поля карточки. CRM-переделы остаются с `bucket = 'crm_stage'`.
  - Порядок карточек считывается из `pc_stage_sequences`.
  - `ensureModeScopedConsistency` повторно группирует задачи по переделам и заполняет `snapshot.modeScoped.crm.stageTasks`.

## 5. Отображение на клиенте
- Клиент получает JSON `/api/state`, `restoreState` применяет `setCrmState` и `applyModeScopedState`.
- Для активного передела выбираются карточки из `modeScoped.crm.stageTasks`. Поскольку `ensureModeScopedConsistency` уже собрала их по стадиям, списки доступны сразу, без дополнительных действий пользователя.

Такой поток гарантирует, что любое изменение, сделанное в CRM или в Планировщике, попадает в SQL и отображается в колонках переделов сразу после загрузки страницы.
