# 📘 Техническое задание v8.2 (окончательная версия)
**Проект:** объединение CRM и Планировщика  
**Цель:** создать единую систему, в которой CRM и Планировщик (Planner_Codex_v3) работают синхронно, используют общую SQL-базу и полностью отображают изменения друг друга в реальном времени.

---

## 1. Основная цель
Объединить **CRM** и **Планировщик** так, чтобы они функционировали как **единая система**:
- В CRM создаются и редактируются заказы (даты, приоритеты, комментарии, переделы и т.д.);
- При переходе в Планировщик (в режиме CRM) пользователь видит **эти же заказы** с переделами;
- Все изменения синхронизируются между CRM и Планировщиком в обе стороны;
- Оба режима (CSV и CRM) используют SQL как основное хранилище данных;
- Интерфейс CRM сохраняет структуру текущего файла **CRM.html**, с минимальными изменениями;
- Реализация объединения может быть любой (общий код, отдельные файлы или новый интерфейс).

---

## 2. Термины
| Термин | Описание |
|--------|-----------|
| **Заказ** | Карточка CRM и строка Планировщика |
| **Передел** | Этап (Лазер, Гибка, Сварка, Мехобработка, Подготовка в работу и т.д.) |
| **Состояние** | Колонка CRM (lane) |
| **Готовность** | Галочка «готово» у заказа или передела |
| **Автооптимизация** | Перестановка заказов при изменениях |
| **Источник данных** | CSV или CRM |
| **Подзаказ** | Дочерний заказ (отображается отдельной строкой) |
| **Мультиборд** | Поддержка нескольких досок (в v1 только `board_key='default'`) |
| **SLA** | Время реакции ≤2 сек на доставку изменений |

## 3. Режимы работы и скорость синхронизации

Добавить в «Общие настройки» Планировщика переключатель:  
**Источник данных: CSV / CRM**  

### CSV-режим  
- Планировщик работает автономно, используя **только таблицу `planner_state`**.  
- **Не выполняет запросов к /api/crm/**.  
- Импорт и экспорт CSV работают как сейчас.  
- Все изменения сохраняются в базу, но **не синхронизируются с CRM**.  

### CRM-режим  
- Планировщик получает данные **только из таблиц `crm_orders` и `crm_stages`** через `/api/crm/*`.  
- **Кнопки «Импорт CSV» и «Импорт состояния» скрыты или недоступны.**  
- Все изменения записываются в SQL и мгновенно отражаются у всех пользователей.  

Настройка скорости синхронизации:
| Режим | Интервал fallback-поллинга | Комментарий |
|--------|-----------------------------|-------------|
| Быстро | 0.5–1 сек | Максимальная отзывчивость |
| Стандарт (по умолчанию) | 1–2 сек | Оптимальный баланс |
| Спокойно | 3–5 сек | Минимальная нагрузка |

## 5. Авторизация и пользователи
**Механизм:** JWT в `HttpOnly` cookie (`SameSite=Strict`, `Secure` в прод). TTL: 24 ч.  

**Эндпоинты:**
- `POST /api/auth/login` — вход;  
- `GET /api/auth/me` — проверка сессии;  
- `POST /api/auth/logout` — выход.  

Ответ при входе:
```json
{ "user": "Имя", "role": "admin|worker|viewer", "token": "...", "expires_in": 86400 }
```

**Роли:**
| Роль | Возможности |
|------|--------------|
| **Админ** | Полный доступ (CRUD, автооптимизация, журнал). |
| **Исполнитель** | Отмечать «готово», менять % выполнения. |
| **Просмотр** | Только чтение. |

Все операции пишут `updated_by` и `updated_at`. Журнал доступен только админам.

## 6. SQL-хранение и миграции

### Принципы  
- Все данные хранятся в одной базе.  
- Таблица `planner_state` — **только для CSV**.  
- В CRM-режиме данные берутся из `crm_orders` и `crm_stages`.  

### Основные таблицы  
`crm_orders`, `crm_stages`, `users`, `activity_log`.

### Расширения таблиц (новое)
```sql
ALTER TABLE crm_orders
  ADD COLUMN priority INT NOT NULL DEFAULT 0,
  ADD COLUMN comments TEXT NULL;

ALTER TABLE crm_stages
  ADD COLUMN comments TEXT NULL;
```

**priority** — числовой приоритет заказа (чем больше, тем выше).  
**comments** — произвольный текст пользователя.  
**priority** используется при автооптимизации как коэффициент сортировки.

### Миграции  
Перед разработкой выполнить создание таблиц (см. SQL-пример в v8).  
Добавить SQL-триггеры для вызова SSE-событий после изменений.

## 7. Архитектура синхронизации (SSE + fallback)

- Основной канал — **SSE (`/api/events`)**.  
- При каждом изменении сервер формирует событие:  
  ```json
  { "type": "update", "entity": "order|stage", "id": 123, "changed": {...}, "by": "user@mail", "timestamp": "...", "version": 42 }
  ```
- Поддерживаются типы: `update`, `reorder`, `bulk`, `state-updated`.  
- При обрыве соединения клиент переходит на fallback-поллинг (по скорости из настроек).  
- **Двусторонняя синхронизация:** любые правки в CRM или Планировщике обновляют SQL и отражаются у всех подключённых клиентов ≤2 сек.  
- Обновление **точечное** — перерисовываются только изменённые строки, без перерисовки всей доски.

### Создание/правка из Планировщика → CRM
- Если пользователь создаёт заказ прямо в конкретном переделе (например, «Гибка»), в CRM создаётся заказ **с единственным переделом «Гибка»**, остальные поля пустые для последующего заполнения.  
- Если к заказу в Планировщике добавлены другие переделы, в CRM они **автоматически появляются** в «Плане переделов».  
- Если не указано состояние — заказ получает `lane = 'Не запланированное'` (в CRM создаётся одноимённая колонка).

---

## 8. Подзаказы и мультиборд

- Подзаказы (`parent_order_id`) отображаются **отдельными строками** под основным заказом (без группировки).  
- Мультиборд отключён в v1: все записи имеют `board_key='default'`.  
- Если локально созданы другие доски — они не синхронизируются с сервером.

## 9. Связь стикеров CRM ↔ поля Планировщика
| Поле CRM | SQL / Планировщик |
|-----------|------------------|
| № заказа | `crm_orders.order_no` |
| Клиент | `crm_orders.customer` |
| Сумма услуг | `crm_orders.service_total` |

| Состояние (колонка) | `crm_orders.lane` |

| Готово (по переделу) | `crm_stages.is_ready` |
| Комментарий (передел) | `crm_stages.comments` |

## 10. Интерфейс CRM

- **Доска:** колонки с карточками заказов.  
- **Карточка:** №, клиент, сумма, готовность, приоритет, комментарий, индикатор переделов.  
- **Редактирование:** окно с таблицей «План переделов».  
- **Переделы по умолчанию:** Лазер, Гибка, Сварка, Мехобработка, Подготовка в работу.  
- **Кнопки:**  
  - «Планировщик»;  
  - «Импорт CSV»;  
  - «Экспорт CSV»;  
  - «Светлая/Тёмная тема».  
- **Уведомления:** `toast` (3–5 сек; зелёный/жёлтый/красный).  
- **Оффлайн:** индикатор 🟡 и автопереподключение SSE раз в 10 сек.

---

## 11. Интерфейс Планировщика

- Кнопка **«CRM»** в шапке.  
- В «Общие настройки»:  
  - Источник данных (CSV / CRM).  
  - Скорость синхронизации (Быстро / Стандарт / Спокойно).  
- **В CRM-режиме:** кнопки «Импорт CSV» и «Импорт состояния» скрыты.  
- **В CSV-режиме:** интерфейс без изменений.  
- Отображается `updated_by`, `updated_at`, `priority` и `comments`.  
- При автооптимизации — пересчёт и сохранение порядка в SQL.  

---

## 12. Ошибки, конфликты и уведомления

- Нет связи → toast + авто-переподключение.  
- Конфликт (409) → модалка: «Обновить / Перезаписать / Сравнить».  
- Ошибки валидации → подсветка полей, блокировка кнопки.  
- Единый UX (`toast` и модалки) в CRM и Планировщике.

---

## 13. Даты и время
- В базе — UTC (TIMESTAMPTZ).  
- В интерфейсе — локальный формат пользователя.  
- Любая правка фиксирует `updated_by` и `updated_at`.

## 14. Импорт, экспорт, бэкапы
- Основной обмен — CSV.  
- JSON — только для локальных бэкапов (не синхронизируется).  
- При импорте JSON → предупреждение:  
  *«Импорт JSON не синхронизируется с сервером. Для обмена используйте CSV.»*

## 16. Безопасность
- JWT в `HttpOnly` cookie (`Secure`, `SameSite=Strict`).  
- Все запросы требуют авторизации.  
- CORS ограничен доверенными доменами.  
- Rate limit на PUT/POST (60 req/мин).  
- Все операции логируются в `activity_log`.  
- Неавторизованные пользователи — только чтение.

## 18. Тест-план
- Создание/редактирование заказов в CRM отображается в Планировщике ≤ 2 сек.  
- Создание/редактирование в Планировщике отражается в CRM.  
- При добавлении нового передела в Планировщике — он появляется в CRM.  
- Заказ без состояния попадает в колонку «Не запланированное».  
- Стикеры CRM отображают реальные данные SQL (часы, даты, проценты, приоритеты).  
- В CRM-режиме скрыты кнопки импорта.  
- JSON-бэкап предупреждает о несинхронизации.  
- `/auth/*` работает корректно, SLA соблюдены.
