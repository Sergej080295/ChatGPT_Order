# Аудит ТЗ v4 по объединению CRM и Планировщика

Ниже — сверка итогового ТЗ v4 с текущим состоянием кода (CRM.html, Planner_Codex_v3.html и server.js). Для каждого раздела фиксирую, что уже реализовано и что ещё надо учесть при разработке.

## 1. Что уже есть в коде

### CRM (CRM.html)
* SPA без сборки: всё хранится в `localStorage` (`mini_crm_v13c`), пользователи могут создавать несколько досок и управлять колонками. 【F:CRM.html†L395-L423】【F:CRM.html†L658-L663】
* Карточка заказа содержит нужные поля (№, клиент, сумма, готовность, даты, прогресс), план переделов редактируется таблично, есть пресет стандартных переделов. 【F:CRM.html†L441-L465】【F:CRM.html†L520-L579】
* Реализованы подзаказы (доли), импорт/экспорт JSON, демо-данные, тема светлая/тёмная. 【F:CRM.html†L445-L655】【F:CRM.html†L664-L694】

### Планировщик (public/Planner_Codex_v3.html)
* Основной режим — работа с CSV или общим JSON-состоянием через `/api/state`; EventSource уже подключён для push-обновлений. 【F:public/Planner_Codex_v3.html†L6-L115】
* Интерфейс содержит таблицу заказов, фильтры, журнал изменений, диалог конфликтов, автооптимизацию и текущие кнопки экспорта/импорта CSV. 【F:public/Planner_Codex_v3.html†L517-L907】【F:public/Planner_Codex_v3.html†L8360-L8461】

### Node.js сервер (server.js)
* Держит одно JSON-состояние планировщика в таблице `planner_state`, журнал пишет в `planner_activity_log`; никаких CRM-таблиц и авторизации нет. 【F:server.js†L12-L220】

## 3. Дополнительные наблюдения
* **Мультиборд в CRM.** ТЗ v4 описывает одну доску с ключом `board_key`, но текущий фронт позволяет неограниченное количество досок и наборов колонок. Нужно решить, переносим ли мультиборд в SQL и как Planировщик выбирает доску.
* **Совместимость с текущим JSON-режимом.** Планировщик использует единый JSON `planner_state`. При вводе CRM-режима нужно решить, будет ли этот JSON формироваться на лету из SQL или таблица останется для CSV-режима.
* **Активность и авторы.** Планировщик уже пишет журнал `planner_activity_log`, но записи формируются фронтендом и не привязаны к реальным пользователям. После внедрения ролей надо унифицировать источник данных журнала (сервер).

## 4. Рекомендации
1. Спроектировать миграции БД для `crm_orders`, `crm_stages`, `users`, `activity_log`, предусмотреть soft-delete и индексы по `updated_at`.
2. Описать архитектуру синхронизации: кто формирует события для Планировщика, какие данные идут через SSE, как выбирается скорость обновлений.
3. Зафиксировать, как мультиборд и подзаказы попадают в SQL и отображаются в Планировщике (отдельные строки, фильтры, группировка).
4. Определить единый подход к уведомлениям об ошибках и конфликтам (например, компонент toast на обеих страницах).
5. Подготовить тест-план и чек-листы под роли, импорт/экспорт CSV, конфликтные изменения и SLA.
