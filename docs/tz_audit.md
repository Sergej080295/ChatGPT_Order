# Аудит ТЗ v7 по объединению CRM и Планировщика

Ниже — сверка финального ТЗ v7 с текущим состоянием кода (CRM.html, Planner_Codex_v3.html, server.js и вспомогательные файлы). Для каждого раздела фиксирую, что уже реализовано и что нужно учесть при дальнейшей разработке.

## 1. Что уже есть в коде

### CRM (CRM.html)
* Одностраничное приложение на чистом JS, данные хранятся в `localStorage` (`mini_crm_v13c`); UI поддерживает несколько досок и колонок, которые пользователь управляет вручную. 【F:CRM.html†L395-L423】【F:CRM.html†L658-L663】
* Карточка заказа содержит поля номера, клиента, суммы, статуса «готово», прогресса и даты; есть модальное окно редактирования с таблицей «План переделов» и пресетом этапов. 【F:CRM.html†L441-L465】【F:CRM.html†L520-L579】
* Реализованы подзаказы («доли»), импорт/экспорт JSON, демо-данные и переключение светлой/тёмной темы. 【F:CRM.html†L445-L655】【F:CRM.html†L664-L694】

### Планировщик (public/Planner_Codex_v3.html)
* Работает с JSON-состоянием и CSV, умеет получать обновления через EventSource (`/api/events`) и локальные/session-режимы. 【F:public/Planner_Codex_v3.html†L6-L174】
* Интерфейс уже содержит таблицу заказов, фильтры, автооптимизацию, журнал изменений, диалог разрешения конфликтов и кнопки импорта/экспорта CSV. 【F:public/Planner_Codex_v3.html†L517-L907】【F:public/Planner_Codex_v3.html†L8360-L8461】

### Node.js сервер (server.js, SERVER_SETUP.md)
* Поднимает API `/api/state`, `/api/events`, `/api/activity`, хранит состояние планировщика в таблице `planner_state`, а историю — в `planner_activity_log`. 【F:server.js†L12-L360】【F:SERVER_SETUP.md†L1-L116】
* Авторизации, CRM-таблиц и пользовательских ролей нет; доступ открыт для всех клиентов. 【F:server.js†L12-L220】

## 3. Дополнительные наблюдения
* **Мультиборд в CRM.** ТЗ v7 фиксирует только `board_key='default'`, но текущий фронт позволяет создавать множество досок и наборов колонок локально. Нужно решить, блокируем ли создание новых досок в UI или синхронизируем их позже. 【F:CRM.html†L395-L423】【F:CRM.html†L658-L663】
* **CSV-режим vs CRM-режим.** Планировщик по-прежнему опирается на `planner_state`. Требуется подтвердить, что таблица остаётся исключительно для CSV, а CRM-JSON формируется бэкендом из `crm_orders`/`crm_stages`. 【F:server.js†L69-L220】【F:public/Planner_Codex_v3.html†L150-L199】
* **SSE-события и порядок.** EventSource выдаёт только обновления `planner_state`, без ссылок на конкретные сущности. Нужно согласовать формат `{type, entity, id, changed, by, timestamp, version}` и хранение порядка после автооптимизации. 【F:public/Planner_Codex_v3.html†L31-L174】【F:public/Planner_Codex_v3.html†L554-L907】
* **Активность и авторы.** Журнал `planner_activity_log` ведётся фронтендом без привязки к реальным пользователям. После внедрения ролей записи следует связать с `users` и перенести логирование на сервер. 【F:server.js†L170-L220】【F:public/Planner_Codex_v3.html†L8360-L8461】
* **JSON-бэкапы CRM.** Интерфейс CRM активно использует JSON-экспорт/импорт. Нужно добавить предупреждение о несинхронизации с сервером и определить, как эти кнопки сочетаются с новым CSV-потоком. 【F:CRM.html†L445-L655】
