# Аудит ТЗ по объединению CRM и Планировщика

## 1. Что есть в коде сейчас

### CRM (Mini CRM v13c)
* SPA на чистом HTML/JS с локальным хранением состояния в `localStorage` (ключ `mini_crm_v13c`). 【F:CRM.html†L396-L414】
* Пользователь может заводить несколько досок со своими колонками, переключаться между ними и редактировать схему статусов. 【F:CRM.html†L380-L606】
* Карточка заказа содержит поля «Название», «№ заказа», «Клиент», «Сумма услуг», «галочка готовности», дату создания/авто-датировки по переделам и заметки. 【F:CRM.html†L520-L599】
* План переделов редактируется таблично (название, даты, часы, % выполнения, готовность); есть пресет базовых переделов. 【F:CRM.html†L547-L579】
* Есть функция разбивки заказа на подзаказы с распределением часов/процентов по переделам, а также отображение долей на карточке. 【F:CRM.html†L607-L655】【F:CRM.html†L445-L451】
* Поддерживаются импорт/экспорт JSON, загрузка демо-данных, тёмная/светлая тема. 【F:CRM.html†L664-L694】

### Планировщик (Planner_Codex_v3)
* Статичная HTML-страница с большим JS-клиентом, ориентированная на CSV-файл и/или синхронизацию единого JSON-состояния через API `/api/state`. Заголовок прямо указывает на режим «CSV only». 【F:public/Planner_Codex_v3.html†L1-L23】
* UI содержит таблицу заказов с множеством сервисных фич (фильтры, бронь, «Автооптимизация», ручные заказы, исключения, журнал изменений, пр.). 【F:public/Planner_Codex_v3.html†L517-L10278】
* Логика работы с «удалённым хранилищем» построена вокруг адаптера `remoteBridge`, который читает/пишет целиком сериализованное состояние и отображает бейдж режима данных (remote/local/session). 【F:public/Planner_Codex_v3.html†L1527-L1742】
* Предусмотрен журнал активности и диалог конфликта версий для параллельных правок. 【F:public/Planner_Codex_v3.html†L8360-L8461】
* Импорт/экспорт CSV уже реализованы, а «Автооптимизация» включается чекбоксом. 【F:public/Planner_Codex_v3.html†L554-L907】【F:public/Planner_Codex_v3.html†L898-L904】

### Node.js сервер
* Работает на Express + PostgreSQL и хранит **одно** JSON-состояние планировщика в таблице `planner_state`; журнал пишет в `planner_activity_log`. 【F:server.js†L12-L128】
* Предоставляет REST/SSE API только для этого состояния (`GET/PUT /api/state`, `GET /api/events`) с примитивным контролем конфликтов по `hash` и `version`. 【F:server.js†L222-L360】
* Нет сущностей CRM (отдельных таблиц заказов/переделов, пользователей и т.п.) и нет авторизации.

## 3. Дополнительные наблюдения
* **Мультиборд и пользовательские статусы.** Сейчас CRM позволяет создавать сколько угодно досок и кастомных колонок. ТЗ описывает одну доску с фиксированными колонками. Нужно решить, поддерживаем ли множественные доски и как они отражаются в Планировщике.
* **Подзаказы/доли.** CRM хранит `childIds`, `partOfPct`, `restOfPct`, `_origValues` для распределения часов. Планировщик сейчас не знает про такие связи. Стоит либо исключить функционал, либо описать, как подзаказы отображаются в Планировщике и в SQL.
* **Доп. поля Планировщика.** Состояние планировщика содержит массу технических флагов (замки, игнорируемые статусы, маршруты, журналы). В ТЗ надо оговорить, какие поля CRM должна поддерживать, а какие останутся чисто планировщику.
* **Импорт/экспорт JSON.** Если JSON-экспорт CRM больше не нужен, это тоже стоит зафиксировать. Иначе — описать, как он соотносится с SQL/CRM режимом.
* **Доступ и аудиторский журнал.** Сервер уже ведёт `planner_activity_log`, но записи формируются фронтендом через `meta`. ТЗ должен определить, кто формирует запись при изменениях в CRM и как связывать её с пользователем.

## 4. Рекомендации по доработке ТЗ
1. Дополнить раздел 5 конкретной схемой БД (таблицы, связи, индексы, soft delete, журнал).
2. Уточнить бизнес-логику мультиборда и подзаказов: оставляем, упрощаем или переносим в Планировщик.
3. Описать, как переключатель CSV/CRM взаимодействует с текущими настройками «локальный кэш / SQL база» и что происходит при отсутствии соединения.
4. Прописать сценарии миграции: импорт существующего CSV в CRM, обратный экспорт, обновление структуры данных.
5. Расширить раздел 11 (безопасность) до полноценной модели авторизации, ролей и хранения пользователей.
6. Зафиксировать требования к уведомлениям/ошибкам для обоих интерфейсов (например, единый toast-компонент вместо `alert`).
7. Добавить требования к API и обмену данными между CRM и Планировщиком (форматы, версии, протокол событий).

Такое уточнение позволит не потерять функционал существующих приложений и заранее закрыть узкие места интеграции.
