# Архитектура и проверка SQL-базы PlanCore

Документ описывает актуальную структуру PostgreSQL после перехода на единую систему хранения заказов. CRM и Планировщик используют один набор таблиц, обновляющийся при каждом сохранении состояния из интерфейса.

## 1. Таблицы

### 1.1 `planner_schema_migrations`
Служебная таблица, в которой фиксируются применённые SQL-миграции. Скрипт `npm run migrate` последовательно выполняет файлы из каталога `migrations/` и добавляет запись о каждом успешно выполненном файле.

### 1.2 `pc_settings`
Ключ-значение с JSON-содержимым. Используется для хранения базовой части снимка (настройки, фильтры, метаданные), конфигурации CRM-досок и последнего вычисленного хеша состояния. Колонки:

* `key` — уникальный идентификатор набора настроек.
* `payload` — JSONB с данными.
* `updated_at` — отметка времени последнего обновления.

Актуальные ключи:

* `snapshot_base` — базовая часть состояния без карточек и задач.
* `crm_boards` — список досок без вложенных заказов.
* `snapshot_hash` — объект `{ hash }` с последним SHA-1 хешем снимка.

### 1.3 `pc_orders`
Хранит карточки заказов вне зависимости от режима отображения. Каждая строка соответствует одному заказу на конкретной CRM-доске.

* `uid` — уникальный идентификатор заказа, используется и в CRM, и в Планировщике.
* `board_id` — идентификатор доски CRM.
* `lane_id` — идентификатор колонки/листа внутри доски (может быть `NULL`).
* `position` — индекс карточки в колонке.
* `payload` — JSONB с полным описанием карточки (клиент, прогресс, метки и т.д.).
* `created_at`, `updated_at` — временные метки.

### 1.4 `pc_order_tasks`
Задачи планировщика. Таблица хранит одинаковые данные для активных, завершённых и архивных задач.

* `uid` — уникальный идентификатор задачи.
* `order_uid` — ссылка на `pc_orders.uid`, если задача связана с заказом (может быть `NULL`).
* `stage_code` — нормализованный код передела.
* `bucket` — список, в котором находится задача (`t`, `done`, `trash`, `exc`, `res`).
* `position` — индекс внутри списка.
* `payload` — JSONB с данными задачи.
* `created_at`, `updated_at` — временные метки.

Индексы `pc_order_tasks_bucket_idx` и `pc_order_tasks_order_idx` ускоряют выборки по списку и заказу.

### 1.5 `pc_stage_sequences`
Для каждого передела хранит упорядоченный массив `task_uids`. Используется для восстановления порядка карточек в канбане Планировщика и в отчётах.

### 1.6 `pc_revisions`
Линейный счётчик ревизий. Каждое успешное сохранение состояния добавляет запись с новым `rev` и хешем снимка.

## 2. Поток обработки `/api/state`

1. Клиент отправляет JSON с полем `state` (строка) или объектом снимка.
2. Сервер парсит снимок, нормализует коллекции и раскладывает данные по таблицам:
   * Настройки и метаданные сохраняются в `pc_settings` (`snapshot_base`, `crm_boards`, `snapshot_hash`).
   * Карточки CRM попадают в `pc_orders` с едиными `uid`.
   * Задачи Планировщика записываются в `pc_order_tasks` с указанием списка и позиции.
   * Порядок карточек по переделам сохраняется в `pc_stage_sequences`.
3. Если хеш входящего снимка совпадает с последним сохранённым, запись в базу пропускается, ревизия не увеличивается.
4. При изменениях создаётся новая запись в `pc_revisions`, а клиентам отправляется SSE-событие с новым номером ревизии и ETag.

## 3. Инициализация и чтение состояния

При запуске `server.js` выполняются миграции и вызывается `loadSnapshotFromDatabase()`:

* `pc_settings.snapshot_base` используется как основа снимка.
* `pc_settings.crm_boards` возвращает список досок.
* Карточки из `pc_orders` распределяются по доскам.
* Задачи из `pc_order_tasks` раскладываются в массивы `t`, `done`, `trash`, `exc`, `res`.
* `pc_stage_sequences` восстанавливает порядок карточек в переделах.
* Если таблицы пусты, возвращается пустой снимок `buildEmptySnapshot()`.

## 4. Проверка работоспособности

1. **Миграции.** Запустите `npm run migrate` и убедитесь, что таблица `planner_schema_migrations` содержит запись `019_rebuild_core_storage.sql`.
2. **Сохранение настроек.** Измените параметры в CRM/Планировщике, нажмите «Сохранить» и выполните запросы:
   ```sql
   SELECT * FROM pc_settings ORDER BY key;
   SELECT * FROM pc_orders ORDER BY board_id, position;
   SELECT * FROM pc_order_tasks ORDER BY bucket, position;
   SELECT * FROM pc_stage_sequences ORDER BY stage_code;
   SELECT * FROM pc_revisions ORDER BY rev DESC LIMIT 5;
   ```
   Новые значения должны появиться во всех таблицах.
3. **Загрузка.** Перезапустите сервер. При первом `GET /api/state` должны вернуться данные из таблиц без дополнительных действий пользователя.
4. **SSE.** Откройте Планировщик в двух вкладках. После изменения в одной вкладке вторая должна получить событие из `/api/events` и обновить состояние.

## 5. Отличия от прежней схемы

* Снимки больше не сохраняются целиком — используется нормализованное хранение заказов и задач.
* CRM и Планировщик читают и записывают одни и те же строки, поэтому изменения доступны сразу во всех разделах.
* Настройки и визуальные конфигурации вынесены в `pc_settings`, избыточные вспомогательные таблицы удалены.
