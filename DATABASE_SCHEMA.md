# SQL-схема планировщика

Документ описывает текущую структуру базы данных PostgreSQL, используемую сервером `planner`. Все изменения применяются миграциями в каталоге `migrations/`, которые исполняются в алфавитном порядке с помощью внутренней таблицы `planner_schema_migrations`.

## 1. Ревизии и аудит

1. Таблица `revisions` хранит каждую ревизию изменений. Колонка `rev` — первичный ключ и получает значение из последовательности `revisions_rev_seq`; дополнительные поля фиксируют время (`ts`) и метаданные исполнителя (`actor`, `source`, `note`).【F:migrations/003_full_sql_schema.sql†L1-L57】
2. Функция `ensure_current_revision()` требует, чтобы во время записи изменений было установлено значение `app.rev`; оно извлекается из текущей транзакции и используется всеми history‑триггерами.【F:migrations/003_full_sql_schema.sql†L320-L362】
3. Таблица `activity_log` фиксирует человекочитаемые события для каждой ревизии (действие, источник, сущность и детализация) и индексируется по `rev`.【F:migrations/003_full_sql_schema.sql†L235-L249】
4. Для каждой основной таблицы существует историческая `_hist` таблица с полным набором колонок базовой таблицы плюс служебные поля `rev`, `op`, `changed_at`. Эти таблицы синхронизируются миграциями 004 и 005, которые гарантируют совпадение схем и пересоздают универсальный history‑триггер.【F:migrations/004_settings_admin_snapshot_retention_backfill.sql†L1-L458】【F:migrations/005_fix_history_tables.sql†L1-L503】
5. Триггеры `*_history_trg` вызывают `generic_history_trigger()` после каждой операции insert/update/delete, автоматически записывая снимок строки в соответствующую `_hist` таблицу под текущей ревизией.【F:migrations/003_full_sql_schema.sql†L364-L452】

## 2. Справочники и настройки

1. `processes` описывает технологические этапы: код, отображаемое имя, позицию в очереди, флаги параллельности и наличия трудозатрат.【F:migrations/003_full_sql_schema.sql†L98-L113】
2. `customers` хранит клиентов (название и внешний `crm_id`).【F:migrations/003_full_sql_schema.sql†L150-L155】
3. Набор таблиц `settings_autoweight`, `settings_journal`, `settings_column_widths`, `settings_mapping`, `settings_admin` и `excluded_statuses` содержит пользовательские настройки интерфейса и фильтров; каждая таблица имеет поле `updated_at` и собственную историческую таблицу для аудита изменений.【F:migrations/003_full_sql_schema.sql†L120-L204】
4. Связи настроек с процессами (`settings_mapping.planner_process_id`) и исключённые статусы используют внешние ключи, что гарантирует согласованность с основными справочниками.【F:migrations/003_full_sql_schema.sql†L134-L204】

## 3. Операционные данные

1. `orders` — центральная таблица заказов: внутренний идентификатор, номер (`number`), опциональный `crm_order_id`, ссылка на клиента, статус и временные метки. Индексы обеспечивают быстрый поиск по статусу и активным заказам.【F:migrations/003_full_sql_schema.sql†L156-L188】
2. `order_process` описывает прохождение заказа по этапам: ссылка на заказ и процесс, порядковый номер (`seq`), плановые и фактические даты, прогресс, флаги готовности и скрытия. Есть индексы по процессу и позиции, а также по паре `(order_id, seq)`.【F:migrations/003_full_sql_schema.sql†L188-L218】
3. `capacity_by_process` хранит доступные минуты на день для каждого процесса и образует ключ `(process_id, day)` для быстрой агрегации мощности.【F:migrations/003_full_sql_schema.sql†L218-L223】
4. Миграции 006–009 выравнивают критичные поля (`status_key`, `customer_id`, `crm_order_id`, `number`) между боевыми и историческими таблицами, обеспечивая корректную работу API и CRM-синхронизации на старых базах.【F:migrations/006_excluded_statuses_status_key_fix.sql†L1-L118】【F:migrations/007_orders_customer_id_fix.sql†L1-L170】【F:migrations/008_orders_crm_order_id_fix.sql†L1-L142】【F:migrations/009_orders_number_column_fix.sql†L1-L133】

## 4. Поток данных сервера

1. При старте сервер выполняет миграции, кэширует максимальную ревизию и обеспечивает наличие обязательных записей настроек (`ensureSettingsDefaults`).【F:server.js†L68-L154】
2. Каждая операция записи выполняется через `runWithRevision()`: генерируется новое значение `rev`, оно фиксируется в `app.rev`, сразу вставляется строка в `revisions`, после чего исполняется пользовательский обработчик. Это гарантирует, что history‑триггеры могут ссылаться на уже существующую ревизию.【F:server.js†L178-L208】【F:server.js†L364-L420】
3. CRUD-операции над заказами, этапами, мощностями и настройками используют обычные SQL‑инструкции (`INSERT ... ON CONFLICT`, `UPDATE`, `DELETE`). При каждом изменении сервер добавляет запись в `activity_log`, что облегчает аудит действий пользователей.【F:server.js†L210-L560】【F:server.js†L980-L1330】
4. Запросы чтения агрегируют состояние из нормализованных таблиц (стадии, заказы, мощности, настройки) и выдаются клиенту в виде JSON без промежуточных JSON‑снимков в базе. Кэш на стороне сервера инвалидируется при каждой новой ревизии.【F:server.js†L156-L362】

## 5. Исторические и вспомогательные объекты

1. Все `_hist` таблицы содержат полный набор колонок базовой таблицы, благодаря функциям пересборки из миграций 004 и 005; при необходимости данные переносятся во временную таблицу и возвращаются в обновлённую структуру.【F:migrations/004_settings_admin_snapshot_retention_backfill.sql†L64-L403】【F:migrations/005_fix_history_tables.sql†L64-L445】
2. Дополнительные миграции настраивают последовательности `revisions_rev_seq` и, при наличии наследованных колонок `id`, корректно связывают их с соответствующими sequence-объектами.【F:migrations/004_settings_admin_snapshot_retention_backfill.sql†L486-L625】【F:migrations/005_fix_history_tables.sql†L458-L503】
3. Миграция 011 удаляет экспериментальную таблицу JSON‑снимков, окончательно фиксируя хранение только в нормализованных SQL-структурах.【F:migrations/011_remove_snapshot_storage.sql†L1-L5】

## 6. Импорт легаси‑снимков

Скрипт `scripts/import_legacy_snapshot.js` загружает старый JSON, очищает основные таблицы, пересоздаёт процессы и заказы, а затем добавляет ревизию через тот же механизм `app.rev`, чтобы история и ограничения оставались консистентными даже на устаревших схемах.【F:scripts/import_legacy_snapshot.js†L1-L204】
