# Гибридное хранение данных Planner Codex

Сервер объединяет **SQLite** и локальный JSON-файл, чтобы снапшоты сохранялись мгновенно и были доступны всем клиентам даже при сбоях диска или откате. SQLite выступает основным источником истины, JSON хранится как резервная копия и точка быстрого восстановления. Ниже описано, как устроена новая схема.

## 1. Структура базы данных SQLite

Файл базы располагается в `data/planner.db`. Его создаёт функция `getDatabase()` при старте сервера и включает `WAL` для безопасной параллельной записи.【F:server.js†L19-L63】

### 1.1 Таблица `snapshots`

| Колонка  | Назначение |
|----------|------------|
| `rev`    | Целочисленный номер ревизии, первичный ключ. Нарастает при каждом успешном сохранении. |
| `hash`   | SHA-1 хеш нормализованного снапшота; используется для ETag и проверки конкуренции. |
| `state_json` | Полный JSON текущего состояния (все заказы, переделы, настройки, CRM). |
| `meta_json`  | Метаданные сохранения (последние авторы, настройки и т. п.). |
| `actor`, `source`, `note`, `channel` | Кто инициировал сохранение и из какого канала пришли данные. |
| `saved_at` | ISO-время последнего обновления записи. |

Запись в таблицу выполняет `writeSnapshotToSql()`, вызываемая как из `persistSnapshotWithSql()`, так и из процедуры гидратации при старте.【F:server.js†L94-L158】【F:server.js†L2685-L2732】

### 1.2 Таблица `kv_store`

Простейшее key-value-хранилище. Пока используется один ключ — `latest_snapshot`, содержащий JSON с номером ревизии, хешем и краткими метаданными. Это позволяет быстро определить актуальную ревизию без разбора полного снапшота.【F:server.js†L130-L158】

### 1.3 Таблица `planner_settings`

Хранит последние общие настройки планировщика (ёмкости, параллельность, режим работы, лимит журнала, карты CRM и т. д.) в виде одной строки с фиксированным идентификатором `1`. Сервер читает её при старте через `readPlannerSettingsFromSql()`, а при любом сохранении снапшота обновляет с помощью `writePlannerSettingsToSql()`. Таблица синхронизируется с `meta.settings` и гарантирует, что изменения из интерфейса не пропадут даже при очистке JSON-файла или импорте другого состояния.【F:server.js†L168-L344】【F:server.js†L2604-L2668】【F:server.js†L3074-L3349】

## 2. Резервный JSON-файл

`data/planner-state.json` синхронизируется с SQLite в обе стороны:

* При чтении сервер сначала пытается получить данные из SQLite (`readSnapshotFromSql()`). Если запись найдена, он обновляет JSON-файл, чтобы локальная копия соответствовала базе.【F:server.js†L2232-L2261】
* Если SQLite пуст (например, после первой установки), сервер читает JSON, нормализует снапшот и сразу записывает его в базу (`writeSnapshotToSql()`), тем самым «поднимая» исходные данные в SQL.【F:server.js†L2263-L2287】

Функция `ensureSqlHydrated()` вызывается при запуске и гарантирует, что кэшированное состояние сохранено в базе даже после аварийного завершения процесса.【F:server.js†L2734-L2748】

## 3. Поток сохранения (`PUT /api/state`)

1. `persistSnapshotWithSql()` нормализует входящий снапшот: приводит коллекции к массивам, создаёт секцию `modeScoped`, помечает хранилище как гибридное и синхронизирует `meta.settings` с таблицей `planner_settings`, получая очищенный набор общих настроек.【F:server.js†L2610-L2670】
2. Сервер вычисляет хеш, получает следующий номер ревизии (на основе кэша и SQLite) и формирует запись со всеми метаданными.【F:server.js†L2671-L2697】
3. `writeSnapshotToSql()` вставляет или обновляет строку в `snapshots` и ключ `latest_snapshot`, а затем перезаписывает JSON-файл резервной копии. Так настройки и снимок данных остаются консистентными во всех слоях хранилища.【F:server.js†L2698-L2716】
4. Кэш `cachedSnapshot` обновляется, а всем подключённым клиентам отправляется SSE-событие с новым `rev` и `hash`, поэтому изменения мгновенно отображаются у всех пользователей.【F:server.js†L3372-L3395】

Если клиент присылает снапшот с устаревшим `hash` (например, без предварительной синхронизации после чужих правок), сервер сравнивает `If-Match`/`baseHash` с актуальным значением и возвращает `HTTP 412 Conflict` без сохранения. Это защищает от «откатов» — данные не перезаписываются устаревшей версией, а клиент получает подсказку повторить попытку после обновления состояния.【F:server.js†L3572-L3590】

## 4. Определение актуальной ревизии

`getLatestRevision()` сначала читает `kv_store`, затем — саму таблицу `snapshots`, и только при отсутствии данных обращается к JSON-файлу. Это упрощает восстановление после удаления файла или базы: любой из источников может воссоздать другой.【F:server.js†L2151-L2169】

## 5. Проверка работы

1. **Запуск сервера.** Выполните `node server.js` — в логах появится путь к файлу SQLite. После первого сохранения убедитесь, что `data/planner.db` обновился по времени изменения.
2. **Проверка ревизий.** С помощью `sqlite3 data/planner.db 'SELECT rev, hash, saved_at FROM snapshots ORDER BY rev DESC LIMIT 5;'` убедитесь, что новые ревизии добавляются.
3. **Сверка JSON.** После изменений сравните хеш из SQLite и из API: `curl -s http://localhost:3000/api/state | jq '.meta.storage.mode'` должен вернуть `"hybrid"`, а хеш из ответа совпадает с `snapshots.hash`.
4. **Резервное восстановление.** Остановите сервер, удалите `data/planner.db` и снова запустите. Снапшот восстановится из `planner-state.json`. Аналогично, при удалении JSON-файла сервер пересоздаст его из SQLite.
5. **Целостность настроек.** Проверьте таблицу `planner_settings`: `sqlite3 data/planner.db 'SELECT settings_json FROM planner_settings'` — содержимое должно совпадать с разделом `meta.settings` из API, включая обновлённый `updatedAt`.【F:server.js†L168-L344】【F:server.js†L2604-L2668】

Такая схема сочетает преимущества SQL (надёжность, контроль ревизий) и резервного JSON (простое восстановление и перенос между окружениями), сохраняя целостность данных CRM, планировщика и настроек в одном источнике истины.
