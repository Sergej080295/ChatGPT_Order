# Архитектура SQL-хранилища Planner (версия 2024-09)

## 1. Общая схема

Начиная с миграции `021_rebuild_normalized_schema.sql` все данные планировщика
хранятся в нормализованном виде без JSON-полей. За каждую ревизию отвечает
таблица `planner_state_snapshots`, а прикладные сущности вынесены в отдельные
таблицы:

| Назначение                         | Таблица                                   |
|-----------------------------------|-------------------------------------------|
| Метаданные снимка                 | `planner_state_snapshots`                 |
| Скаляры состояния                 | `planner_state_scalars`                   |
| Мощность по операциям             | `planner_state_capacity`                  |
| Признак параллельности операций   | `planner_state_parallel`                  |
| Перекрытия по этапам              | `planner_state_route_overrides`           |
| Скрытые статусы                   | `planner_state_ignored_states`            |
| Списки заказов/элементов          | `planner_state_list_entries` + `..._attributes` |
| CRM-секции                        | `planner_state_crm_values`                |
| Раздел `modeScoped`               | `planner_state_mode_scoped_values`        |
| Техническое `meta`                | `planner_meta_values`                     |
| Журнал изменений                  | `planner_meta_history_entries` + `..._attributes` |
| Общие настройки                   | `planner_settings`                        |
| Пользовательские флаги            | `planner_preferences`                     |

Все таблицы, содержащие ссылку на ревизию, привязаны к `planner_state_snapshots`
через `ON DELETE CASCADE`, поэтому очистка истории выполняется простым
удалением из таблицы снимков.

## 2. Ключевые таблицы

### 2.1 `planner_state_snapshots`
Одна строка на ревизию (`rev`, внешний ключ на `revisions`). Содержит хеш
состояния и время создания. Любое сохранение вызывает UPSERT, поэтому повторное
сохранение ревизии обновляет `created_at`.

### 2.2 Скаляры и агрегаты
- `planner_state_scalars` — простые значения верхнего уровня (процесс,
  фильтры, флаги автоопераций и т. д.). Хранятся типизированно с колонками
  `value_type/value_text/...`.
- `planner_state_capacity` и `planner_state_parallel` — численные и булевы
  характеристики по кодам операций.
- `planner_state_route_overrides` — сохранённые интервалы по ключу
  `parentId::stage`.
- `planner_state_ignored_states` — список скрытых статусов.

### 2.3 Списки и сущности
`planner_state_list_entries` содержит строки для массивов (`t`, `done`, `trash`,
`exc`, `res`, а также вспомогательных списков). Каждая запись хранит
идентификаторы родительского/дочернего заказа и позицию в списке. Детальные
свойства лежат в `planner_state_list_entry_attributes`, где структура
разворачивается по JSON Pointer аналогично прежним `planner_snapshot_entries`.

- `orders` записывается как упорядоченный список пар «этап → массив UID». Сам
  этап дублируется в колонке `parent_order_id`, а массив UID хранится в
  атрибутах (`uids`).
- `locked` — линейный список UID, значения сохраняются непосредственно в
  `order_identity` без дополнительных атрибутов.

### 2.4 Техническое `meta`
- `planner_meta_values` — плоское хранение полей `meta` без истории и настроек.
- `planner_meta_history_entries` — журнал изменений; основные поля (`actor`,
  `source`, `summary`, `event_time`) вынесены в отдельные колонки, детали — в
  таблицу атрибутов.

### 2.5 CRM и прочие разделы
`planner_state_crm_values` и `planner_state_mode_scoped_values` повторяют логику
атрибутов: путь, тип и значение.

### 2.6 Настройки
- `planner_settings` — структурированные настройки `meta.settings`/`settings`.
  Значение `null` хранится отдельной строкой с пустым путём.
- `planner_preferences` — булевы флаги (автосохранение, уведомления и т. п.).
  Поля `updated_at`/`updated_by` фиксируют автора изменения.

## 3. Поток сохранения и чтения

1. `persistSnapshotWithSql` вычисляет хеш и вызывает `persistSnapshotData`.
2. `persistSnapshotData`:
   - записывает строку в `planner_state_snapshots`;
   - очищает все таблицы состояния для ревизии (`clearStateForRevision`);
   - распределяет данные по специализирующимся таблицам (скаляры, списки,
     CRM, meta, история и т. д.);
   - обновляет `planner_settings` и `planner_preferences`.
3. Чтение (`loadSnapshotRevision`) собирает объект в обратном порядке: скаляры,
   списки, CRM, meta + история, затем применяет общие настройки.

## 4. Администрирование

`DELETE /api/admin/history` удаляет все строки из `planner_state_snapshots`
(с `CASCADE`), если не найдено снимков для сохранения. При наличии актуального
снимка происходит выборочное удаление `WHERE rev <> $1`, что каскадно очищает
все дочерние таблицы. Откат (`POST /api/admin/rollback`) считывает снапшот по
хешу, формирует новую ревизию и заново прогоняет процедуру сохранения.

## 5. Миграции и запуск

1. Подготовьте PostgreSQL и выполните `npm run migrate`. Миграция `021` создаст
   новую схему и удалит устаревшие таблицы (`planner_snapshot_entries`,
   `planner_general_settings` и др.).
2. При первом запуске `npm start` сервер поднимет пул и прочитает последнюю
   ревизию через `loadLatestSnapshot()`.
3. Скрипт `scripts/import_legacy_snapshot.js` адаптирован под новую схему и
   использует те же вспомогательные функции, что и сервер: данные из JSON
   разворачиваются по таблицам `planner_state_*` без хранения текстового JSON.

Новая структура избавляет от универсальных EAV-таблиц и упрощает работу с
административными инструментами: каждая функциональная зона (списки заказов,
настройки, журнал) хранится отдельно, что повышает читаемость и ускоряет
выборки.
