# Архитектура и проверка SQL-базы Planner

## Версия схемы: 2024-07 (миграции `018_rebuild_snapshot_entries.sql` + `019_create_general_settings.sql`)

Комбинация миграций `018` и `019` полностью пересобирает SQL-хранилище планировщика. Скрипт `018`
удаляет устаревшие таблицы/последовательности, создаёт заново `revisions`, `planner_snapshots` и
универсальную таблицу `planner_snapshot_entries` без JSON-полей. Миграция `019` добавляет
`planner_general_settings`, куда выносится раздел общих настроек, и переносит в неё данные из
последнего снапшота. Итоговая схема даёт типизированное хранение как состояния, так и настроек.
【F:migrations/018_rebuild_snapshot_entries.sql†L1-L61】【F:migrations/019_create_general_settings.sql†L1-L33】

## 1. Основные таблицы и их роль

### 1.1 Служебные таблицы
- **`planner_schema_migrations`** — журнал применённых SQL-скриптов. Создаётся автоматически перед
  запуском миграций и предотвращает повторное выполнение уже применённых файлов.【F:server.js†L172-L214】
- **`revisions`** — счётчик ревизий с привязкой к автору, источнику и заметке. Поле `rev` берётся из
  последовательности `revisions_rev_seq`, которая принадлежит таблице; строки добавляются как во
  время миграций, так и при каждом сохранении состояния или импорте.【F:migrations/018_rebuild_snapshot_entries.sql†L9-L27】【F:server.js†L228-L275】

### 1.2 Снимки планировщика
- **`planner_snapshots`** — одна строка на ревизию с SHA‑1 хешем состояния и отметкой времени
  создания. Хеш используется в заголовках ETag и для поиска по истории. При повторной записи ревизии
  строка обновляется, а `created_at` переустанавливается на текущий момент.【F:migrations/018_rebuild_snapshot_entries.sql†L29-L43】【F:server.js†L831-L905】
- **`planner_snapshot_entries`** — универсальное хранилище значений без JSON: каждая запись содержит
  ревизию, категорию (`state` или `meta`), путь (совместимый с JSON Pointer), тип значения, текстовое
  либо числовое/булево представление и порядковый номер для элементов массивов. Именно сюда попадает
  весь снимок после развёртки в «плоскую» форму; при чтении данные собираются обратно в объект.
  Категория `state` отвечает за рабочее состояние, `meta` — за технические отметки (автор, источник,
  заметки и т.п.).【F:migrations/018_rebuild_snapshot_entries.sql†L45-L61】【F:server.js†L831-L921】

### 1.3 Общие настройки
- **`planner_general_settings`** — отдельная таблица для раздела «Общие настройки». Структура
  повторяет формат `planner_snapshot_entries`, но без привязки к ревизиям: ключ `path` (в формате
  JSON Pointer без префикса `meta/settings`), тип значения и представления для строк/чисел/булевых,
  а также `ordinal` для массивов. Таблица заполняется либо миграцией `019`, либо сервером при каждом
  сохранении снапшота, а в колонке `updated_by` фиксируется автор изменения.【F:migrations/019_create_general_settings.sql†L1-L33】【F:server.js†L734-L813】

## 2. Поток записи и чтения снапшотов

1. **Получение следующей ревизии.** Любая операция записи оборачивается в `runWithRevision()`,
   которая выделяет номер из `revisions_rev_seq`, создаёт строку в `revisions` и выполняет переданный
   обработчик в транзакции. После фиксации ревизия кэшируется для SSE-уведомлений.【F:server.js†L697-L784】
2. **Сохранение снимка.** `persistSnapshotData()` глубоко копирует объект состояния, вырезает из него
   `meta.settings`/`settings`, сериализует оставшиеся данные и записывает их в `planner_snapshots` и
   `planner_snapshot_entries` (категории `state` и `meta`). Общие настройки передаются в
   `persistGeneralSettings()`, которая полностью заменяет содержимое `planner_general_settings`, тем
   самым гарантируя единственный источник правды без JSON-полей.【F:server.js†L734-L864】
3. **Чтение снапшота.** `loadSnapshotRevision()` загружает хеш из `planner_snapshots`, собирает
   структуру из таблицы `planner_snapshot_entries`, подтягивает текущие общие настройки из
   `planner_general_settings` и возвращает полноценный объект состояния (включая
   `snapshot.meta.settings`). Функция `loadMetadataForRevisions()` аналогично восстанавливает
   метаданные сразу для нескольких ревизий, что используется в истории изменений.【F:server.js†L866-L922】【F:server.js†L922-L949】
4. **История и очистка.** Эндпоинты `/api/admin/history` и `/api/admin/history/:hash` работают только
   с новыми таблицами; при очистке истории (`DELETE /api/admin/history`) данные удаляются из обеих
   таблиц (`planner_snapshot_entries`, `planner_snapshots`) одной командой `TRUNCATE` или выборочно по
   условию `rev <> $1`.【F:server.js†L1233-L1422】

## 3. Проверка корректности базы после деплоя

Выполните следующие шаги, чтобы убедиться, что новое хранение работает стабильно:

1. **Миграции.** Запустите `npm run migrate` — в таблице `planner_schema_migrations` должны появиться
   строки для `018_rebuild_snapshot_entries.sql` и `019_create_general_settings.sql`. Если база
   пустая, в логе появится сообщение об успешном применении и создании ревизии для миграции.【F:server.js†L172-L227】
2. **Проверка записи снапшота.** Сохраните изменения из интерфейса или выполните запрос `PUT /api/state`.
   Убедитесь, что в `planner_snapshots` появилась свежая строка, а в
   `planner_snapshot_entries` — записи для категорий `state` и `meta` с совпадающим `rev`.
   Пример запросов:
   ```sql
   SELECT rev, hash, created_at FROM planner_snapshots ORDER BY created_at DESC LIMIT 5;
   SELECT category, COUNT(*) FROM planner_snapshot_entries GROUP BY category;
   ```
3. **История.** Откройте `/api/admin/history` или выполните SQL-запрос на последние ревизии —
   возвращаемые метаданные должны совпадать с полями `actor/source/note`, переданными при сохранении.
   ```sql
   SELECT s.rev, s.hash, r.actor, r.source, r.note
     FROM planner_snapshots AS s
     LEFT JOIN revisions AS r ON r.rev = s.rev
    ORDER BY s.created_at DESC
    LIMIT 10;
   ```
4. **Откат.** Вызовите `/api/admin/rollback` с существующим `hash` и убедитесь, что появляется новая
   ревизия, а таблица `planner_snapshot_entries` содержит данные и для исходного, и для откатного
   снапшота (каждая категория дублируется на новый `rev`). Таблица `planner_general_settings` при
   откате не переписывается автоматически, поэтому общий раздел настроек остаётся в последнем
   сохранённом состоянии — его можно обновить отдельным сохранением или из интерфейса.
5. **SSE и кэш.** При открытии нескольких клиентов один из них должен получать события `revision`
   после сохранения другим — это подтверждает корректную работу кэша и расчёта ETag на основе хеша.

## 4. Мини-инструкция по запуску Планировщика на новой базе

1. **Подготовьте PostgreSQL.** Создайте базу данных и пользователя (по умолчанию используется
   `postgresql://planner:planner@localhost:5432/planner`). Включите SSL, если это требуется окружением.
2. **Настройте окружение.** Установите зависимости `npm install`, выставьте переменные окружения
   `DATABASE_URL`, `PGSSL`/`PGSSLMODE` при необходимости и, при большом числе соединений,
   параметр `PGPOOL_MAX`.【F:server.js†L14-L28】
3. **Примените миграции.** Запустите `npm run migrate` — скрипт `run_migrations.js` создаст таблицу
  миграций, применит все SQL-файлы по порядку и гарантирует, что схема соответствует версии 2024-07.【F:server.js†L172-L227】
4. **Запустите сервер.** Выполните `npm start`. При старте сервер прогреет кэш `cachedSnapshot`,
   подтянет последний снапшот из базы и начнёт обслуживать API и статический фронтенд из папки
   `public`.【F:server.js†L300-L359】
5. **Проверьте сохранение.** Любые изменения (из CRM, планировщика или административных страниц)
   отправляются на `/api/state` и попадают в `planner_snapshot_entries`, а общие настройки — в
   `planner_general_settings`. История доступна с любой страницы, потому что сервер использует единый
   поток записей через `persistSnapshotWithSql`. При проблемах проверьте логи сервера и корректность
   настроек подключения к PostgreSQL.【F:server.js†L1058-L1339】

Следуя этим шагам, база остаётся консистентной, данные сохраняются и доступны вне зависимости от
точки входа (CRM, интерфейс планировщика, административный раздел).
