# Архитектура проекта

## Общая схема

Проект — Node.js/Express приложение с SQLite-хранилищем и фронтендом без сборщика. Основной UI расположен в `public/CRM.html`, вспомогательные стили и shell-логика — в `public/plan-core.css` и `public/plan-core.js`.

```text
Браузер
  ├─ /login
  ├─ /CRM.html
  ├─ fetch /me, /api/state, /admin/*
  └─ SSE /api/events

Node.js server.js
  ├─ Express routes
  ├─ auth/session middleware
  ├─ SQLite better-sqlite3
  ├─ snapshot persistence
  ├─ planner settings mirror
  └─ audit log

Каталог data/
  ├─ planner.db
  ├─ credentials.json
  └─ служебные файлы/экспорты
```

## Структура репозитория

```text
.
├── package.json              # зависимости и команды запуска
├── server.js                 # сервер, API, SQLite, авторизация, сохранение состояния
├── public/
│   ├── CRM.html              # основной фронтенд CRM/планировщика
│   ├── plan-core.css         # общие стили оболочки
│   └── plan-core.js          # тема, версия, UI-оболочка
├── lib/
│   └── bcryptjs.js           # fallback bcryptjs
├── data/
│   ├── credentials.json      # seed пользователей/ролей
│   └── planner.db            # SQLite база в runtime
└── documentation/            # документация передачи проекта
```

## Сервер

`server.js` отвечает за:

- автоподключение/установку зависимостей при необходимости;
- настройку Express и compression;
- выбор каталога данных;
- SQLite-схему;
- авторизацию, сессии и роли;
- REST API состояния;
- SSE-уведомления о ревизиях;
- аудит;
- защиту от конфликтов записи по hash/ETag;
- обработку ошибок прав записи в `data/`.

### Сохранение состояния

Основной endpoint записи — `PUT /api/state`. Клиент отправляет JSON-снимок состояния. Сервер:

1. валидирует payload;
2. проверяет права `write`;
3. проверяет режим записи и канал;
4. сравнивает ожидаемый hash с текущим;
5. при конфликте возвращает `412`;
6. записывает snapshot в SQLite;
7. обновляет cached snapshot;
8. отправляет SSE-событие с новой ревизией.

### Конфликты записи

Если клиент пишет поверх устаревшей ревизии, сервер возвращает `412 Conflict`. UI должен подтянуть свежий snapshot и повторить действие только если это безопасно.

### Ошибки прав на диск

Если SQLite или каталог данных недоступны на запись, сервер возвращает `507 StoragePermission` с сообщением: «Сервер не может записать данные CRM. Проверьте права доступа к каталогу data/.».

## Фронтенд

`public/CRM.html` — монолитный HTML+CSS+JS. Это важная особенность сопровождения:

- нет webpack/vite/build-step;
- большинство функций находятся в одном `<script>`;
- перед рефакторингом обязательно искать вызовы через `rg`;
- синтаксис проверяется извлечением последнего `<script>` и `new Function(script)`.

### Основные зоны фронтенда

| Зона | Назначение |
| --- | --- |
| Bootstrap | авторизация, получение начального состояния, выбор remote/local source. |
| Константы CRM | переделы, настройки по умолчанию, роли UI, форматирование. |
| Sanitizers | нормализация состояния, настроек, календарей, заказов. |
| Storage | localStorage fallback и remote save через API. |
| Rendering | CRM-доска, таблицы, страницы переделов, Гант, маршрут. |
| Settings | список переделов, вместимость, параллельность, календарь, экспорт/импорт. |
| Admin | пользователи, роли, аудит. |
| Event handlers | кнопки, формы, drag/drop, фильтры, чекбоксы готовности. |

## Динамический каталог переделов

Приложение имеет фиксированные исторические ключи переделов и пользовательские пресеты. Функция динамического каталога сопоставляет пользовательские переделы с внутренними ключами или создает новые `custom_*` ключи.

Критично:

- пользовательский «Список переделов» — источник истины для UI настроек;
- старые заказы могут содержать удаленные переделы/этапы;
- диагностика таких данных выполняется через «Конфликты данных»;
- при изменении каталога нужно проверять права `stageAccess`, вместимость, параллельность и Гант.

## Расписание и Гант

Расписание строится на основе:

- списка заказов;
- стадий заказа;
- трудоемкости или прогресса;
- вместимости/параллельности;
- исключений и брони;
- замороженных/ручных сегментов;
- автодат и сдвига `autoDateOffsetDays`.

Гант использует рассчитанные сегменты и должен синхронно отображать левую колонку заказов и календарную сетку. Любые изменения размеров строк/колонок нужно проверять и на странице передела, и на общей странице Ганта.

## Синхронизация клиента

Клиент работает с remote snapshot через `/api/state` и получает обновления ревизий через `/api/events`. Есть localStorage fallback. Потенциальные причины «отката» данных:

- конфликт `412` и последующее применение старого snapshot;
- локальный fallback поверх remote данных;
- sparse/full merge настроек с дефолтами;
- несколько открытых вкладок с разными ревизиями;
- ошибка записи `507`;
- сессия истекла и запись не прошла.

## Версия UI

Версия отображается в `public/plan-core.js` через `PLANECORE_VERSION`. Экспорт настроек также содержит поле `version`.
