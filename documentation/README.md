# Планировщик / PlanCore CRM — документация для передачи проекта

Документация подготовлена как пакет для передачи проекта другой команде разработки. Она описывает назначение приложения, пользовательские сценарии, архитектуру, хранение данных, API, зоны риска, диагностику и историю ключевых изменений версий `v5.6.x → v5.7`.

## Быстрый старт для новой команды

1. Прочитать этот файл и `PROJECT_OVERVIEW.md`.
2. Поднять приложение локально по инструкции из раздела «Запуск» ниже.
3. Изучить пользовательские сценарии в `USER_GUIDE.md`.
4. Разобрать архитектуру и точки расширения в `ARCHITECTURE.md`.
5. Проверить API, хранение и права в `API_AND_STORAGE.md`.
6. При поиске багов пользоваться `QA_TROUBLESHOOTING.md`.
7. Для понимания последних доработок и причин изменений открыть `VERSION_HISTORY.md`.
8. Для практической передачи разработки использовать `DEVELOPMENT_HANDOVER.md`.

## Запуск локально

Требования:

- Node.js `>=18`.
- npm.
- Права на запись в каталог `data/` или альтернативный каталог через `DATA_DIR`.

Команды:

```bash
npm install
node server.js
```

После запуска сервер слушает порт `3000` по умолчанию. CRM открывается через `http://localhost:3000/CRM.html`, но без активной сессии будет редирект на `/login`.

## Проверки перед передачей изменений

Минимальный набор проверок после правок:

```bash
node --check server.js
node --check public/plan-core.js
node - <<'NODE'
const fs=require('fs');
const html=fs.readFileSync('public/CRM.html','utf8');
const scripts=[...html.matchAll(/<script[^>]*>([\s\S]*?)<\/script>/gi)].map(m=>m[1]).filter(s=>s.trim());
new Function(scripts[scripts.length-1]);
console.log('CRM script syntax ok');
NODE
git diff --check
```

Для ручного smoke-теста сервера:

```bash
node server.js
curl -I http://localhost:3000/CRM.html
```

Ожидаемо без авторизации CRM вернет `302` на `/login`.

## Самые важные правила сопровождения

- Любые изменения переделов нужно проверять вместе с настройками вместимости, параллельных операций, правами по переделам, Гантом и списком заказов.
- Не заполнять настройки вместимости/параллельности фантомными дефолтными ключами: список в UI должен соответствовать пользовательскому «Списку переделов».
- При изменении сохранения данных обязательно проверять конфликт `412`, ошибку прав `507`, SSE-обновления и отсутствие отката значений после refresh.
- При изменении стадий/этапов обязательно проверять миграцию старых заказов и окно «Конфликты данных».
- Перед удалением или переименованием функции искать все вызовы через `rg`, так как фронтенд расположен в одном большом HTML-файле.
