# Проверка одновременного редактирования Планировщика/CRM

Набросок простых сценариев для ручной проверки того, что изменения разных пользователей не теряются и не затирают друг друга.

1. **Исключения vs. Бронь (разные разделы)**
   - Пользователь A добавляет исключение на дату `D1` в переделе со сменой.
   - Пользователь B одновременно добавляет бронь на дату `D2` в другом переделе.
   - Оба сохраняют данные.
   - Ожидание: после обновления у обоих видны и исключение, и бронь без потерь.

2. **Разные строки в одном разделе**
   - Пользователь A ставит исключение на `D1` для передела X.
   - Пользователь B ставит исключение на `D2` для того же передела X.
   - Оба сохраняют данные.
   - Ожидание: оба исключения остаются в списке, порядок не важен.

3. **Одна и та же дата/поле (конфликт)**
   - Пользователь A меняет значение исключения на дате `D1` для передела X.
   - Пользователь B почти одновременно меняет ту же дату `D1` в том же переделе X.
   - При сохранении одного из пользователей возникает конфликт.
   - Ожидание: появляется предупреждение о параллельных изменениях и предложение обновить данные/повторить сохранение; тихой потери данных нет.

4. **Изменения в CRM-заказах и календарях одновременно**
   - Пользователь A двигает карточку заказа между колонками.
   - Пользователь B добавляет бронь/исключение в календарь переделов.
   - Оба сохраняют.
   - Ожидание: движение карточки и изменения календаря сохраняются, если изменения не пересекаются; при пересечении отображается предупреждение о конфликте.

5. **Сохранение при устаревшем снапшоте**
   - Пользователь A сохраняет любые правки и обновляет состояние.
   - Пользователь B, имея старое состояние, пытается сохранить свои правки, пока A уже сохранил новые данные.
   - Ожидание: система либо объединяет непересекающиеся изменения, либо сообщает о конфликте, предлагая обновить данные, без молчаливого перезаписывания свежего состояния.
