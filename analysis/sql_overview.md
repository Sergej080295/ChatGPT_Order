# SQL инфраструктура планировщика

## 1. Источник данных: SQL или JSON?

После последних правок сервер собирает состояние `/api/state` из нормализованных SQL-таблиц. Монолитный JSON (`planner_state.state`) остаётся как кэш и резервная копия для начальной загрузки и отката при сбоях, но не является источником истины для задач, исключений, мощностей или настроек. Каждый `PUT /api/state` транзакционно:

1. Сливает новые настройки с текущими (`mergeSettingsSnapshot`).
2. Обновляет профиль планировщика и связанные сущности в базе (`persistSnapshotToSql`).
3. Сохраняет обновлённый JSON-снимок только как бэкап/кеш (`planner_state`).

Таким образом, рабочие данные живут в SQL, а JSON используется для совместимости и аварийного восстановления.

## 2. Действующие таблицы

| Таблица | Назначение | Ключевые поля и особенности |
| --- | --- | --- |
| `planner_schema_migrations` | Сервисная таблица миграций. | `filename` — уникальный идентификатор миграции, `applied_at` — время применения. Позволяет применять миграции идемпотентно. |
| `stage_type` | Справочник переделов/стадий. | `code` (уникальный), `name`, `sort_order`, `is_active`. Обновляется при каждом снимке на основе фактических данных. |
| `customer_order` | Заказы из CRM. | `order_no` (уникален в паре с `is_deleted`), `title`, `client`, `priority`, дедлайны, флаг `is_deleted`. Связан с `order_stage`. |
| `order_stage` | Стадии заказа для построения Ганта. | `order_id` → `customer_order`, `stage_type_id` → `stage_type`, длительность, даты, статусы, прогресс, `external_uid`, версия. Содержит JSON-поле `payload` для полного снимка задачи. |
| `stage_completion` | История завершения стадий. | Ссылка на `order_stage`, время завершения, источник и заметка. Используется для журнала «Готово». |
| `stage_exception` | Исключения и блокировки. | `kind`, `details` (JSONB), даты создания/закрытия, ссылка на стадию. |
| `capacity_by_stage` | Производственные мощности по переделам. | `stage_type_id` (PK), `capacity_per_day`, `updated_at`. Пересчитывается из настроек. |
| `parallel_limits` | Ограничения параллельной работы. | `code` (PK), `max_parallel`, `updated_at`. Также синхронизируется с настройками. |
| `planner_settings` | Глобальные настройки планировщика. | `autosave_on`, `auto_optimize_on`, `shift_on_progress`, `storage_mode`, `extra` (JSONB с остальными настройками), `updated_at`. |
| `planner_activity_log` | Журнал изменений. | `timestamp`, `stage`, `version`, `user_name`, `session`, `source`, `summary`, `diff`, `orders_summary`, `ip`. Индексы по времени и стадии для отчётности. |
| `planner_state` | Кэш и бэкап монолитного JSON. | `state` (строка JSON), `meta`, `hash`, `updated_at`. Используется при первичной инициализации и в SSE/ETag ответах. |

Всего активно используется 11 таблиц.

## 3. Поток обновления настроек

* Клиент отправляет только изменённые ключи (`meta.settings.entries`) и, при необходимости, флаг `replace` для очистки отсутствующих значений.
* Сервер выполняет точечный merge, обновляя как `meta.settings`, так и синхронизированные поля (`capByProc`, `parallelByProc`, флаги автосохранения).
* `persistSnapshotToSql` переносит настройки в `planner_settings`, а мощности/параллельность — в профильные таблицы.
* SSE-уведомления рассылают дельты; клиенты подтягивают свежий снимок и мгновенно получают актуальные настройки.
