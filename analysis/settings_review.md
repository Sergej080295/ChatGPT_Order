# Отчет по потенциальным проблемам

## Потенциальная причина потери настроек
- Серверный обработчик `PUT /api/state` всегда заменяет целиком снимок состояния и поле `meta`, не пытаясь слить настройки.
- Если два клиента (или две вкладки) сохраняют настройки по очереди, поздний запрос, собранный на основе устаревшего снимка, перезапишет более свежие значения.
- Фронтенд уже передаёт в `meta.settings` список изменённых ключей и их значения, что позволяет реализовать merge/replace без полной перезаписи.

## План исправления
1. В `PUT /api/state` добавить ветку `if (meta?.stage === 'settings')`.
2. В ней: загрузить текущий JSON из базы, распарсить `state.meta.settings` и объединить его с новыми значениями из `meta.settings.entries` (по умолчанию merge).
3. Если `meta.settings.replace === true`, очищать отсутствующие ключи перед применением новых значений.
4. После слияния сериализовать обновлённый снимок и только затем обновлять `planner_state`.
5. Покрыть ветку unit-тестами: последовательные PATCH‑ы с разными ключами, конфликтный сценарий replace, проверка версий.

## Текущее состояние базы данных
- База — PostgreSQL. Таблица `planner_state` хранит целиком JSON-снимок (поле `state`), сопроводительные данные (`meta`, `hash`, `updated_at`).
- Журнал изменений (`planner_activity_log`) ведётся в той же БД и использует JSONB для diff/summary.
- Таким образом, хранилище работает в режиме «SQL + монолитный JSON-снимок».
