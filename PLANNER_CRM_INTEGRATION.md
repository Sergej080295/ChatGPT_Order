# Интеграция Планировщика и CRM (PlanCore)

Документ описывает, как новое приложение PlanCore объединяет CRM‑доски и производственные переделы, используя поэлементные API и
SQLite‑хранилище.

## 1. Источник данных

* **Процессы** (`GET /api/processes`) — справочник переделов с кодами и позициями. Клиент использует их для построения кнопок и
  определения текущего этапа.
* **Заказы** (`GET /api/orders`) — список заказов с идентификаторами, номерами и статусами. На фронтенде они отображаются как строки
  таблицы и карточки маршрута.【F:server.js†L422-L519】【F:public/Planner_Codex_v3.html†L274-L439】
* **Маршруты заказов** (`GET /api/order-process`) — детализированные этапы каждого заказа с плановыми и фактическими датами. Эти
  данные необходимы для таблицы передела, диаграммы Ганта и общего маршрута.【F:server.js†L549-L662】【F:public/Planner_Codex_v3.html†L441-L575】
* **Порядок переделов** (`GET /api/planner/stage-orders`) — массив `order_uids`, сохраняющий сортировку карточек по переделам.
  При отсутствии данных клиент реконструирует порядок по датам, но при сохранении он должен отправить `PATCH` с `ifVersion`.【F:server.js†L664-L746】【F:public/Planner_Codex_v3.html†L169-L233】
* **CRM‑доски и мета** (`GET /api/crm/boards`, `/api/crm/orders-meta`) — используются в CRM‑интерфейсе для отображения lane и связок
  заказов с досками.【F:server.js†L707-L926】【F:public/CRM.html†L1-L186】

## 2. Версионирование и конфликтология

Каждая строка таблицы имеет `row_version`, который клиент обязан передать в `ifVersion` при обновлении. Несовпадение версий
приводит к `409 Conflict` с актуальной строкой в теле ответа — UI может пересчитать дельту и повторить запрос. Это касается
обновлений заказов, маршрутов, переделов и пользовательских настроек.【F:server.js†L422-L519】【F:server.js†L549-L746】

## 3. Подписка на изменения

Маршрут `/api/events` открывает SSE‑подключение и рассылает пакеты вида:

```json
{
  "rev": 42,
  "orders": [{ "id": 5, "row_version": 3, "data": { ... } }],
  "order_process": [{ "id": 12, "row_version": 6, "data": { ... } }],
  "stage_orders": [{ "stage_code": "bend", "order_uids": ["order-5"], "row_version": 8 }]
}
```

Фронтенд обновляет локальный кэш без повторных запросов и перерисовывает таблицу, диаграмму и маршруты. В PlanCore список
переделов, таблица заказов и Гант синхронизируются в обработчике `applyDelta()`。【F:server.js†L357-L413】【F:public/Planner_Codex_v3.html†L577-L646】

## 4. Отображение данных в Планировщике

* **Таблица передела** (`renderOrdersTable`) отображает отфильтрованные задачи текущего передела, отмечает опоздания и готовность.
  Фильтр (`current`, `all`, `done`, `late`) применяется на клиенте без дополнительных запросов.【F:public/Planner_Codex_v3.html†L276-L355】
* **Диаграмма Ганта** (`renderGantt`) строит полосы на основе плановых дат. Если данных недостаточно, выводится сообщение.
  Цвета отражают статус: готово, опоздание или активная работа.【F:public/Planner_Codex_v3.html†L357-L424】
* **Общий маршрут** (`renderRoutes`) собирает все переделы выбранного заказа и показывает прогресс по каждому этапу.
  Состояние рассчитывается локально из `order_process` без дополнительных API вызовов.【F:public/Planner_Codex_v3.html†L426-L508】

## 5. CRM‑интерфейс

`public/CRM.html` использует те же REST‑эндпоинты для чтения досок (`/api/crm/boards`), метаинформации (`/api/crm/orders-meta`) и
заказов (`/api/orders`). Это обеспечивает единый источник истины: любые изменения, зафиксированные через PlanCore, мгновенно
попадают в CRM‑панель и обратно.【F:public/CRM.html†L1-L186】

## 6. Расширение

* Для новых пользовательских настроек используйте `settings_shared_preferences` (булевые флаги) или `planner_misc_state` (произвольный
  JSON). Сервер уже содержит `PATCH`‑эндпоинты и проверку версий.【F:server.js†L664-L815】
* Для сохранения пользовательского порядка карточек отправляйте `PATCH /api/planner/stage-orders/:stageCode` с массивом UID и
  `ifVersion`. Сервер ведёт историю изменений (`stage_order_history`) для последующего анализа алгоритмов автооптимизации.【F:server.js†L664-L746】

Такая архитектура исключает устаревшие снапшоты, ускоряет синхронизацию и делает фронтенд независимым от массивных JSON‑ответов —
каждый компонент читает только нужные сущности, а SSE доставляет минимальные дельты.
